# Project-context (глоссарий)

**Upstream:** https://github.com/mattpocock/skills (MIT), skill `engineering/domain-modeling`.  
**Adapter, не клон:** берём только идею короткого `CONTEXT.md`-глоссария. Без ADR-форматов,
без `CONTEXT-MAP.md`, без Claude slash-commands. На русском, под хаб.

## Когда

- В целевом репо обсуждаются термины предметной области (Customer vs User, Order vs Cart…).
- Нужно зафиксировать словарь, чтобы не путаться между сессиями.

## Когда НЕ

- Workspace **это хаб** `C:\Users\artyo\.cursor` — **запрещено** создавать `CONTEXT.md` в хабе.
  Хаб живёт под `AGENTS.md` + `SYSTEM-REGISTRY.md`. Этот skill в хабе не пишет.
- Однострочный фикс, разовый ответ — не нужен файл.
- Уже есть `CONTEXT.md` — правь его, не плоди второй.

## Файл

- Путь: `CONTEXT.md` в корне целевого репо. Если корень уже шумный — `docs/CONTEXT.md`.
- Содержимое — **только глоссарий**. Без имплементации, без спек, без ADR.
- Формат:

```markdown
# Контекст <проект>

- **Термин** — одно слово/фраза определения. Без эссе.
- **Customer** — платящий аккаунт; не то же, что User (логин).
```

## Поведение

1. Услышал размытый/перегруженный термин → предложи точный канонический. «Ты говоришь
   "аккаунт" — это Customer или User? Это разные сущности».
2. Согласовали термин → сразу запиши в `CONTEXT.md`. Не копи пакетом — по одному.
3. Если код противоречит глоссарию — подсвети: «В коде отменяется весь Order, а ты сказал
   возможна частичная отмена. Что верно?»
4. Не создавай ADR на каждое решение. ADR — только если (а) трудно откатить,
   (б) будущий читатель удивится, (в) был реальный выбор. Иначе просто запись в глоссарий.
